# Запуск в контейнерах

Файлы кладутся в корень репозитория SRW (рядом с `New_Sipuha/`):

```
SRW/
├── docker-compose.yml
├── .env
├── .dockerignore
├── deploy/
│   └── Dockerfile
└── New_Sipuha/
```

## Что уже поправлено в коде

- `New_Sipuha/core/worker.py` — адрес RabbitMQ читается из `RABBITMQ_HOST`, был
  захардкожен как `localhost`. Redis там уже брался из переменной.
- `New_Sipuha/requirements.txt` — добавлен `pydantic-settings`, его импортирует
  `settings/config.py`.

## Запуск

```bash
cp .env.example .env      # заполнить JWT_SECRET_KEY
docker compose up --build
```

Первая сборка долгая: torch тянет около гигабайта даже в CPU-варианте.

- API: http://localhost:8000/docs
- RabbitMQ: http://localhost:15672 (guest / guest)

Проверка цепочки:

```bash
docker compose logs -f worker
```

Должно появиться «Универсальный воркер (PYTORCH) успешно запущен».

## Ключевые решения

**Общий каталог для файлов.** `routes/audio.py` кладёт загруженный файл во временный
каталог и передаёт воркеру только путь. В контейнерах у каждого сервиса свой `/tmp`,
и воркер файла не увидит. Поэтому обоим сервисам проставлен `TMPDIR=/data/audio`,
а туда примонтирован общий том — `tempfile` уважает эту переменную, код менять не
пришлось.

**torch ставится отдельно.** В `requirements.txt` он идёт без указания индекса, и pip
тянет CUDA-сборку весом под 3 ГБ. В Dockerfile сначала ставится CPU-версия с
`download.pytorch.org/whl/cpu`, дальше остальные пакеты видят зависимость
удовлетворённой.

**Порядок запуска.** Воркер и API подключаются к брокеру сразу при старте и падают,
если он не готов. Поэтому у rabbitmq и redis прописаны healthcheck, а зависимые
сервисы ждут `service_healthy`.

**База.** `DATABASE_URL` указывает на `/data/db/users.db` в отдельном томе, иначе
пользователи будут пропадать при каждой пересборке.

## Настольное приложение

Остаётся на хосте, в контейнеры не заводится: в контейнере оно потеряло бы доступ
к звуковой карте и потребовало проброса X11, не дав ничего взамен. Запускается как
раньше — `./run.sh` из своего каталога.

## Что осталось несделанным

Настольное приложение и бэкенд пока никак не связаны: приложение считает всё
локально своей заглушкой, а `POST /audio/detect` живёт сам по себе. Чтобы связать,
в приложение нужно добавить режим отправки на сервис: получить токен, отправить
файл, опросить `GET /audio/result/{request_id}`. Это отдельная задача, в
контейнеризацию она не входит.
